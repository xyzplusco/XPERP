# XP ERP — 권한 체계 재설계 기획

작성: 2026-08-19 · 라이브 DB 실측 기준

---

## 1. 지금 상태 (문제)

| 항목 | 현재 |
|---|---|
| 역할값 | `admin` / `partner` / `member` / `external_contributor` |
| 실제 계정 | 1개 (yks@xyzplus.co = admin, 윤권상 연결) |
| **읽기 권한** | **21개 테이블 전부 `xp_is_member()` — 계정만 있으면 전부 열람** |
| 쓰기 권한 | admin은 전부 / 그 외는 자기 프로젝트만 |
| 계정 생성 | 터미널 `npm run user:create` 만 가능 |

**핵심 문제: 읽기에 역할 구분이 없다.**
지금 PL 계정을 발급하면 그 사람이 전사 매출·모든 계약서·모든 프로젝트를 볼 수 있다.
쓰기만 막혀 있을 뿐이다. 이건 설계 누락이다 — 처음 만들 때 "로그인한 내부 인원"만 구분했고
"내부 인원 안에서의 등급"은 구분하지 않았다.

## 2. 제안 — 역할 4단계

말씀하신 3단계에 `열람전용`을 하나 더 두는 것을 권한다. 임원처럼 **보기만 하고 건드리면 안 되는**
사람이 반드시 생기는데, 그때 staff를 주면 데이터가 망가진다.

| 역할 | 대상 | 데이터 범위 | 쓰기 | 계정 관리 |
|---|---|---|---|---|
| `owner` **마스터 어드민** | 대표 1명 | 전부 | 전부 + 영구삭제 | **가능** |
| `staff` **임직원 (경영지원)** | 경영지원팀 | 전부 | 전부 (영구삭제 제외) | 불가 |
| `member` **PL / PM** | 프로젝트 담당자 | **자기 프로젝트 범위만** | 자기 프로젝트만 | 불가 |
| `viewer` **열람전용** | 임원·감사 | 전부 (매출 포함) | 없음 | 불가 |

- `owner`는 1개만 존재하도록 DB에서 강제 (부분 유니크 인덱스)
- 기존 `yks@xyzplus.co`(admin) → `owner`로 승격
- 기존 `partner` / `external_contributor` 값은 쓰이지 않으므로 정리

## 3. member(PL/PM)가 보는 범위

여기가 이번 작업의 본체다. 테이블별로 "내 프로젝트"를 기준으로 좁힌다.

| 데이터 | member 범위 | 근거 |
|---|---|---|
| 프로젝트 | 내가 PL·PM·구성원인 것만 | 요청사항 그대로 |
| 주간 업데이트 / 액션 / 회의록 | 그 프로젝트 것만 | 프로젝트에 종속 |
| 고객사 | 내 프로젝트의 고객사만 | 프로젝트 통해 파생 |
| 문서·계약서 | 내 프로젝트 것만 | 계약서는 민감 |
| **파트너 명부** | **전체 열람 (권장)** | ↓ 아래 설명 |
| **이벤트** | **전체 열람 (권장)** | ↓ 아래 설명 |
| **매출 금액** | **숨김 (권장)** | ↓ 아래 설명 |
| 휴지통 | 자기가 버린 것만 | |
| 계정 목록 | 자기 것만 | |

### 판단이 필요한 3가지 — 제 의견

**파트너 명부는 전체 공개를 권합니다.**
XP의 핵심 자산이 네트워크입니다. PL이 "이 건에 맞는 전문가가 누구지"를 못 찾으면 일이 안 됩니다.
연락처까지는 열되, **그 사람의 NDA·위촉계약 문서는 막습니다** (문서는 별도 규칙).

**이벤트도 전체 공개를 권합니다.**
파트너스데이·얼라인먼트데이는 전사 행사입니다. 숨기면 오히려 참여가 떨어집니다.

**매출 금액은 숨기는 것을 권합니다.**
예상매출·계약금액이 가장 민감하고, PL 실무에 꼭 필요하지도 않습니다.
member 화면에서는 금액 열 자체를 걷어냅니다.

> **솔직히 짚을 점**: Postgres RLS는 *행* 단위지 *열* 단위가 아닙니다.
> 매출 열 숨김은 앱에서 안 보여주는 방식이라 **실수 방지 수준**이지 완전 차단이 아닙니다.
> 완전 차단이 필요하면 member 전용 뷰를 따로 파야 하는데, 관리 비용이 큽니다.
> 내부 임직원 대상이므로 앱 레벨 숨김으로 충분하다고 봅니다. 필요하면 나중에 뷰를 분리합니다.

## 4. 계정 관리 화면 (터미널 제거)

`설정 → 계정` 을 마스터 어드민 전용으로 확장한다.

```
계정 관리                                          [+ 계정 추가]

이메일                역할        연결 파트너   상태    최근 로그인
──────────────────────────────────────────────────────────────
yks@xyzplus.co       마스터      윤권상        활성    2026-08-19    [비밀번호 재설정]
ksm@xyzplus.co       PL/PM       김수민        활성    2026-08-18    [역할변경] [비활성화]
```

**계정 추가 폼**

```
이메일        [ ksm@xyzplus.co        ]
연결 파트너   [ 김수민 ▾ ]  ← 파트너 DB 검색. 연결해야 담당 프로젝트가 잡힙니다
역할          ( ) 마스터 어드민  (•) 임직원  ( ) PL/PM  ( ) 열람전용
초기 비밀번호 [ 자동 생성 ▾ ]  → 생성 후 1회만 화면에 표시
              [ ] 첫 로그인 시 비밀번호 변경 요구
```

- 생성 즉시 로그인 가능 (이메일 인증 없음 — 내부 도구)
- 초기 비밀번호는 **생성 직후 한 번만** 표시, DB에는 해시만 저장
- 비활성화하면 로그인 차단 (데이터는 유지)
- 삭제는 마스터 어드민만, 확인 절차 후

### 기술 전제 — 새로 필요한 것 하나

Supabase Auth 사용자를 앱에서 만들려면 **service_role 키**가 필요합니다.
현재 앱은 anon 키만 쓰고 있어서 계정 생성이 불가능합니다.

```
SUPABASE_SERVICE_ROLE_KEY=...     ← 서버 전용 (NEXT_PUBLIC_ 접두어 없음)
```

- Vercel 환경변수에 등록 필요
- **server action 안에서만** 사용, 브라우저로 절대 나가지 않음
- 이 키는 RLS를 무시하므로 계정 생성/삭제 외 용도로는 쓰지 않는다

이게 이번 기획의 유일한 새 인프라 요구사항입니다.

## 5. 작업 순서

**1단계 — 역할 체계 (마이그레이션)**
- `global_role` 허용값 변경: owner / staff / member / viewer
- owner 1명 강제, yks@xyzplus.co 승격
- `xp_is_owner()`, `xp_is_staff()` 헬퍼 추가, `xp_is_admin()`은 owner+staff로 재정의

**2단계 — 읽기 범위 좁히기 (핵심)**
- `xp_my_project_ids()` 함수 추가
- projects / weekly / tasks / meeting_notes / documents / companies 의 SELECT 정책 재작성
- people / events는 전체 유지
- **검증: member 계정으로 남의 프로젝트가 안 보이는지 실제 확인**

**3단계 — 계정 관리 화면**
- service_role 키 연결
- 계정 추가 / 역할 변경 / 비밀번호 재설정 / 비활성화 UI
- 터미널 스크립트는 비상용으로 남김

**4단계 — 화면 반영**
- member에게 매출 열 숨김
- 사이드바에서 권한 없는 메뉴 숨김 (휴지통·설정 등)

---

## 6. 되돌릴 수 없는 것 / 주의

- 읽기 정책을 좁히면 **기존 화면 일부가 member에게 빈 목록으로 보인다.** 의도된 동작이지만
  PL이 "고장났다"고 오해하지 않도록 빈 상태 문구를 명확히 해야 한다.
- `owner`를 1명으로 강제하면 그 계정을 잃었을 때 복구가 곤란하다.
  → 비상 복구 경로(터미널 스크립트)를 반드시 남긴다.
- service_role 키가 유출되면 DB 전체가 열린다. Vercel 서버 환경변수로만 두고 절대 클라이언트 노출 금지.
